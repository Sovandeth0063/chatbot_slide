Introduction & Challenges & Goals

What We Built?

An AI-powered multilingual (Khmer/English) customs chatbot for the GDCE (General Department of Customs and Excise).

Challenges

Information Is Scattered & Hard to Find

Too Much Time Spent on Repeated Questions

Inconsistent Answers to the Same Question

Help Is Only Available During Office Hours

Goal

Build a complete AI-powered customs chatbot that autonomously "help " in handling customs questions, calculates import duties and taxes, retrieves trade statistics, and surfaces legal procedures all grounded in official GDCE documents, available in both Khmer and English, 24/7.

Why Embeddings Are Needed

Embeddings convert Khmer/English queries and document passages into numerical vectors that capture semantic meaning. This enables the system to retrieve relevant customs information even when the user’s wording differs from the document, improving cross-lingual search, semantic matching, and RAG answer accuracy.

Khmer benchmark (BGE-M3, Jina v3, Qwen3-Embedding): arxiv.org/abs/2605.22099 · General multilingual context (BGE-M3 vs. mE5-L, LaBSE): arxiv.org/abs/2605.23618

End-to-End Pipeline, API & Reliability
GDCE
01

Data Ingestion & Embedding

  • Multi-format document parsing (PDF page-aware extraction, Markdown)
  • Section/header-boundary chunking with sentence-level fallback for oversized text, configurable overlap
  • Batched embedding generation (BAAI/bge-m3, 1024-dim), memory-safe grouped processing (avoids OOM)
  • Incremental, checkpointed vector-store upload (crash-safe resume)
02

Query Understanding

  • Unicode-based language detection (Khmer/English)
  • Domain abbreviation expansion (CIF, VAT, ATIGA, HS code, etc.)
  • Cross-lingual term mapping for embedding search
  • Regex-based intent gating — detects trade-analytics queries missing a time period, triggers clarification instead of guessing
03

Retrieval & Reranking

  • Cosine-similarity ANN search, hybrid semantic + structured/keyword fusion, deduplication
  • Custom multi-signal reranker: token-overlap ratio, exact-phrase boost, exact-question boost, domain dispute-term boosts, metadata-chunk penalty; scores normalized and re-sorted
04

Answer Generation

  • 3-stage LLM cascade: primary LLM (auto-retry on empty response with reduced context) → self-hosted fallback → extractive snippet fallback
  • Prompt design splits "must-cite-context" (regulatory facts) vs. "general-knowledge-allowed" (conceptual) answering to reduce hallucination
  • Redis-cached responses (keyed on query + doc IDs) to skip redundant LLM calls
05

API & Reliability

  • REST endpoints: retrieval, health check, service info — Pydantic-validated requests/responses
  • Domain exception hierarchy mapped to proper HTTP status codes (validation, rate limit, service unavailable, etc.)
  • Configurable via ~30 environment variables (timeouts, thresholds, model selection, rate limits, CORS)
  • Session-ID passthrough for request tracing
06

Evaluation & Load Testing

  • 39 automated tests (unit + API integration, fully mocked backends)
  • Two load-testing tools (async ramp tester + Locust) tracking p50/p95/p99 latency and failure-rate to find concurrency ceiling

GDCE
01

Classification Flow

  • Parallel execution: Gemini HS-prefix extraction (6-digit family) + semantic vector search — reduces latency
  • Structured prefix lookup scans in-memory corpus for matching codes; falls back to semantic search if prefix extraction fails
02

Scoring & Domain Filters

  • Lexical reranking: token overlap, 4-digit heading match, exact domain terminology ("spark-ignition," "marine," "diesel-electric")
  • Vehicle constraint inference: fuel type, body type, engine displacement, drive type, CBU/CKD assembly — strict filtering with automatic relaxation fallback
  • Semantic results merged in when structured results are sparse (<3 candidates), deduplicated
03

Answer Generation

  • Gemini produces ranked HS codes, explanation, generic-query warnings, clarifying questions, official tariff reference URL
  • Returned codes validated against actual retrieved candidates (guards against hallucination)
  • Runs in worker thread (sync SDK); falls back to extractive ranking if Gemini fails/disabled
04

Embeddings & Caching

  • Lazy-loaded, process-cached sentence-transformer model, deterministic hash-based fallback if model fails to load
  • Three-tier corpus cache: in-process memory → persistent cache → full Qdrant scroll
  • Batch upload pipeline (256-point batches) for populating Qdrant
05

API & Reliability

  • POST /hs-code-candidates (full results), POST /hs-code-ranked (compact answer), GET /health, GET /
  • Fail-open caching, session_id echo-only (no conversation memory), health endpoint doesn't live-check dependencies
  • Output framed as decision support — verify against official GDCE tariff or a specialist
06

Evaluation

  • Automated test suite (helpers + API, mocked backends); async ramp tester + Locust load testing, latency percentiles tracked

GDCE

Execution sequence of the Unified Sequential Slot-Collection Gate inside the Calculator handler resolving missing slots dynamically.

Turn 01

Product Identification

User Request

"hs code of iphone?"

  • Intent: Extract entity & lock type
  • NLU Resolution: hs_code_lookup, entity="iphone"
  • Session Cache: Save last_entity="iphone"
  • Candidate: ["8517.13.00"] saved to Redis
Response

Returns matching HS candidate list

Turn 02

Pronoun Resolution & Missing Slots

User Request

"calculate its import tax"

  • Co-reference: Resolve pronoun "its" → "iphone"
  • Rewritten: "calculate import tax for iphone"
  • Slot Gate: hs_code unconfirmed, cif_value missing
  • State: Set pending_clarification=True
Ask-Back Response

"Ask user to confirm one of the following HS code options, and the price user spend"

Turn 03

HS Lock & Next Missing Slot

User Request

"8517.13.00"

  • Validation: Match against candidate_codes
  • Slot Lock: Confirm hs_code="8517.13.00"
  • Slot Gate: hs_code OK, cif_value still MISSING
Ask-Back Response

"What is the price that user paid"

Turn 04

Formula Execution & Persist

User Request

"$1000"

  • Slot Lock: Parse price → cif_value=1000
  • DB Fetch: Get duty rates (CD=0%, ST=5%, VAT=10%)
  • Formula: Execute ceiling rounding math
  • Persist: Save conversation + telemetry to DB
Final Response

SSE streams iphone's tax breakdown

Search queries are progressively narrowed down by using only the delta, while the session automatically maintains the product context.

Candidate Retrieval

User Request

"hs code of car?"

  • Intent: hs_code_lookup, entity="car"
  • Retrieval: Orchestrator calls Retrieval Service (Port 8003)
  • Vector Search: Embeds query → searches Qdrant :6333 (gdce_hs_code)
Response

returns candidates in 8703.xx.xx, entity = car

Turn 02

Context Refinement & Re-ranking

User Request

"its fully assembled"

  • Query Rewriter: Detects follow-up & enriches with car context
  • Rewritten: "hs code for assembled car"
  • Re-ranking: Retrieval Service narrows results to 8703.xx.xx
  • Session Cache: Saves last_entity="fully assembled car", candidate_codes=["8703.xx.xx"]

Returns narrowed candidate: The hs list narrows to other-than-CKD

User Request

"Is there a more specific subheading under that?"

  • Co-reference: Resolves pronoun "that" → "fully assembled car"
  • Rewritten: "fully assembled car subheadings HS code"
  • Bilateral Check: Searches 8-digit AHTN extensions under 8703.23.xx

Returns 8703.23.xx subheading

Conclusion & Recommendations
GDCE

Phase 1 delivers a production-grade, bilingual RAG/NLU platform across HS classification, tax calculation, trade statistics, and FAQ retrieval, but the Orchestrator remains a single-shot classifier, not a true agent.

Current Limitation

  • One Intent Per Turn Compound requests (e.g. HS lookup + tax calc) need multiple exchanges
  • No Tool Composition Calculator, Retrieval, Trade, General are hardcoded destinations, not selectable capabilities
  • Validation Without Deliberation Guards reject bad output but can't reason about why it failed
  • Procedural Clarification Fixed slot sequence is a state machine, not a reasoned decision

Recommendation: Agentic Architecture

  • Sub-Agent Services Each service can call other tools when it needs info it doesn't have
  • MCP Discovery Discover tools via MCP instead of hardcoded routes in coordinator.py
  • Orchestrator-Worker Model Hard recursion cap (~3 nested levels)
  • Reason → Act → Observe Self-verify output before finalizing
  • Auditable Call Trees parent_call_id extending service_calls telemetry

Migration Path

Wrap existing services as MCP servers → single-level delegation first → add nested calling behind a depth cap (Retrieval → Calculator) → shadow mode → selective cutover for compound/ambiguous queries.
