The Challenge: Trade Documents at Customs Scale
GDCE
  • Five document types arrive as digital or scanned PDFs: invoices, packing lists, bills of lading, truck bills, airway bills
  • Mixed quality, mixed languages (Khmer, English, Chinese), no standard layout across vendors or countries
  • Goal: automated pipeline from scan to validated JSON, ready for SAD comparison

Pain Points That Block Automation
GDCE
  • Volume: thousands of declarations daily, each backed by multiple supporting documents
  • Manual entry: slow, expensive, and prone to transcription errors that cascade downstream
  • Layout chaos: borderless tables, merged cells, stamps, handwriting; every vendor formats differently
  • Traditional OCR fails: reading order, table structure, and page geometry are lost
  • Downstream cost: bad extraction produces bad JSON, which triggers false mismatches or missed risks
KEY INSIGHT

The core problem is not recognition accuracy alone; it is structural fidelity across diverse, low-quality scans.

JSON Conversion LLM: Qwen3-4B Wins on Efficiency
GDCE

Text-only structured field extraction: temp 0.1, top-k 1, thinking disabled

Model Params / Quant Modality Verdict
Qwen3-4B-Instruct-FP8 4B, FP8 Text-only ✅ Selected
Gemma-3-4b-it 4B Multimodal Comparable accuracy, unnecessary vision overhead
Qwen3.5-4B 4B Multimodal No gain over text-only
Qwen2.5-7B-Instruct-AWQ 7B, AWQ Text-only 75% more VRAM, no accuracy gain
KEY FINDING

Larger models and multimodal input did not improve schema compliance. Output consistency and resource efficiency matter more than parameter count.

Temperature: an LLM generation setting that controls randomness. Low values (0.1 here) make output more deterministic and consistent; high values allow more varied, creative text. For structured field extraction, low temperature reduces inconsistent or hallucinated values.

  • Conditional resolution scaling: factor-28 grid alignment with [min_pixels, max_pixels] bounds
  • Lossless PNG encoding: preserves thin grid lines and stamps

GDCE

Limitations: Why Simple Rules Fail
GDCE

Importer Name

DB entry is what was declared, not what's on the document — hard to tell typos from real errors

Delivery Terms (Incoterms)

FOB vs. DAP are both valid; system can't tell a legitimate restatement apart from a mistake

Total Invoice Amount

Totals change by incoterm (FOB ≠ DAP); comparing across different terms is invalid

Item Mapping

Some DB items use formulas (e.g., "3-8", "6+9") — OCR errors break the lookup

KEY INSIGHT

No single rule catches all cases. Each field gets a tolerance, weight, and context — the decision engine balances competing signals to separate real fraud from valid variances.
