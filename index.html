Orchestrator: 7-Stage Process Flow
GDCE
Stage 01

User Query & Caching

Starts the request, assigns a tracking ID, and locks the session and verify cache hit.

Stage 02

Validation & Normalization

Corrects typos, checks safety, and rejects off-topic queries early.

Stage 03

Unified NLU & Intent

Identifies the user's goal, selects Khmer/English, and asks for clarification if vague.

Stage 04

Context-Aware Rewrite

Merges the current question with chat history.

Stage 05

Microservice Routing

Dispatches the polished query to the best-suited backend service.

Stage 06

Downstream Execution

Fetches regulations (RAG), looks up tariffs, trade statistic or computes tax duties.

Stage 07

SSE Streaming & Persist

Streams the answer live to the screen, then saves the conversation to the database.

Real Testing: Multi-Turn Ask-Back Flow (Calculation)
GDCE

Execution sequence of the Unified Sequential Slot-Collection Gate inside the Calculator handler resolving missing slots dynamically.

Turn 01

Product Identification

User Request

"hs code of iphone?"

  • Intent: Extract entity & lock type
  • NLU Resolution: hs_code_lookup, entity="iphone"
  • Session Cache: Save last_entity="iphone"
  • Candidate: ["8517.13.00"] saved to Redis
Response

Returns matching HS candidate list

Turn 02

Pronoun Resolution & Missing Slots

User Request

"calculate its import tax"

  • Co-reference: Resolve pronoun "its" → "iphone"
  • Rewritten: "calculate import tax for iphone"
  • Slot Gate: hs_code unconfirmed, cif_value missing
  • State: Set pending_clarification=True
Ask-Back Response

"Ask user to confirm one of the following HS code options, and the price user spend"

Turn 03

HS Lock & Next Missing Slot

User Request

"8517.13.00"

  • Validation: Match against candidate_codes
  • Slot Lock: Confirm hs_code="8517.13.00"
  • Slot Gate: hs_code OK, cif_value still MISSING
Ask-Back Response

"What is the price that user paid"

Turn 04

Formula Execution & Persist

User Request

"$1000"

  • Slot Lock: Parse price → cif_value=1000
  • DB Fetch: Get duty rates (CD=0%, ST=5%, VAT=10%)
  • Formula: Execute ceiling rounding math
  • Persist: Save conversation + telemetry to DB
Final Response

SSE streams iphone's tax breakdown

Initial Query Extraction

User Request

Relative Reference Resolution

GDCE

Search queries are progressively narrowed down by using only the delta, while the session automatically maintains the product context.

Turn 01

Candidate Retrieval

User Request

"hs code of car?"

  • Intent: hs_code_lookup, entity="car"
  • Retrieval: Orchestrator calls Retrieval Service (Port 8003)
  • Vector Search: Embeds query → searches Qdrant :6333 (gdce_hs_code)
Response

returns candidates in 8703.xx.xx, entity = car

Turn 02

Context Refinement & Re-ranking

User Request

"its fully assembled"

  • Query Rewriter: Detects follow-up & enriches with car context
  • Rewritten: "hs code for assembled car"
  • Re-ranking: Retrieval Service narrows results to 8703.xx.xx
  • Session Cache: Saves last_entity="fully assembled car", candidate_codes=["8703.xx.xx"]
Response

Returns narrowed candidate: The hs list narrows to other-than-CKD

Turn 03

Specific Subheading Lookup

User Request

"Is there a more specific subheading under that?"

  • Co-reference: Resolves pronoun "that" → "fully assembled car"
  • Rewritten: "fully assembled car subheadings HS code"
  • Bilateral Check: Searches 8-digit AHTN extensions under 8703.23.xx
Response

Returns 8703.23.xx subheading

Conclusion & Recommendations
GDCE

Phase 1 delivers a production-grade, bilingual RAG/NLU platform across HS classification, tax calculation, trade statistics, and FAQ retrieval, but the Orchestrator remains a single-shot classifier, not a true agent.

Current Limitation

  • One Intent Per Turn Compound requests (e.g. HS lookup + tax calc) need multiple exchanges
  • No Tool Composition Calculator, Retrieval, Trade, General are hardcoded destinations, not selectable capabilities
  • Validation Without Deliberation Guards reject bad output but can't reason about why it failed
  • Procedural Clarification Fixed slot sequence is a state machine, not a reasoned decision

Recommendation: Agentic Architecture

  • Sub-Agent Services Each service can call other tools when it needs info it doesn't have
  • MCP Discovery Discover tools via MCP instead of hardcoded routes in coordinator.py
  • Orchestrator-Worker Model Hard recursion cap (~3 nested levels)
  • Reason → Act → Observe Self-verify output before finalizing
  • Auditable Call Trees parent_call_id extending service_calls telemetry

Migration Path

Wrap existing services as MCP servers → single-level delegation first → add nested calling behind a depth cap (Retrieval → Calculator) → shadow mode → selective cutover for compound/ambiguous queries.
